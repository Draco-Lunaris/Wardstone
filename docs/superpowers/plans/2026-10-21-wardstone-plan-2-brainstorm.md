# Wardstone Plan 2 — brainstorming record

Working notes for the Plan 2 design pass (API + auth + certificate profiles).
Decisions land here as they are made, with the reasoning, so the eventual plan
and spec can be written from this rather than reconstructed from a transcript.

Status: **design complete.** All open questions answered — 26 settled decisions
below. Next step is writing the Plan 2 spec from this record, then the
implementation plan.

### D18. First-run setup is IN Plan 2, and it is a SETUP PAGE

The first-run setup is a **product feature the spec already commits to**
("first-run wizard names the CA, asks only what's needed, then Wardstone
issues its own UI TLS certificate from its own CA — full clean self-issued
TLS from first boot"). It is not a Plan 2 vs Plan 3 question, and deferring
it would be scope-cutting on a settled decision. *(Controller had briefly
framed the bootstrap as deferrable and was corrected.)*

**The setup page is the ONLY place the admin credential is ever
established.** The user types the first admin's username and password into
it, along with the default domain. That credential is never generated by
the system, never printed to a log, never written to a config file, and
never delivered out-of-band.

*(Controller had proposed generating a random admin password and printing it
once to the logs, and a config file carrying admin credentials. Both were
rejected as unacceptable: a credential that exists in a log file or on disk
in plaintext is a credential that leaks via log aggregation, backups, or
`docker logs`.)*

**Consequences:**

- The setup surface must be reachable and must accept a password — so it
  is the spec's "plain HTTP on the LAN, bound to a setup port, for the
  setup session only" window, with the setup banner the spec describes.
  The spec rejected the alternative (a self-signed cert before the wizard)
  precisely because it would teach users to click through TLS warnings on
  the very page where they enter admin credentials.
- The setup endpoint is **only live while unconfigured**. Once the tenant
  exists it is not merely refused — it is not routed.
- The password is stored only as an argon2 hash (the house pattern). It
  exists in plaintext only in the request body, in flight.
- The setup page also establishes the **default domain** (D3), which
  scopes the default profile.

**Still open:** whether the setup page in Plan 2 is served by `ws-web`
(a minimal first-run page, with the full UI arriving later) or by
`ws-api`; and whether Plan 2 also mints the server's own TLS certificate
from the new CA (the spec ties the UI's cert to the wizard's restart onto
HTTPS, which only fully makes sense once the UI exists).

### D19. The setup page is served over HTTPS with a self-signed cert, swapped for a real one at completion

*(Owner decision, 2026-10-21 — overturns the spec's "bootstrap TLS window"
builder's call, which had specified plain HTTP during setup.)*

The spec rejected the self-signed alternative because it "teaches users to
click through TLS warnings on the very page where they'll enter admin
credentials." The owner's counter-argument, which is stronger on the
security property that actually matters:

- **Plain HTTP during setup sends the admin password across the LAN in
  cleartext.** Anyone on the same network can capture the first credential
  of the whole system — the one that can then issue certificates.
- **A self-signed cert keeps the setup page encrypted.** The browser
  warning is a one-time, *visible* signal; the encryption is permanent.
- **The cert is swapped at completion.** Setup creates the root, issues a
  real leaf for the server's hostname, and ws-web switches to it. The spec's
  own sequence already ends with "restarts ws-web onto HTTPS only" — the
  swap is a restart with a different cert source, not new machinery.

**The fingerprint option (worth adopting):** generate the self-signed cert
with the correct SAN and have the setup page display its SHA-256
fingerprint so the operator can verify it out-of-band — the same
trust-on-first-use pattern the spec already requires for the step-ca token
flow ("a SHA-256 fingerprint of Wardstone's leaf cert pinned in the wizard
UI"). The operator then *verifies* the cert rather than clicking through a
warning.

**Open sub-question:** the self-signed setup cert's private key must exist
on disk for the restart to survive, which is the same "key on disk" concern
the keystore work addressed. Mitigations: it is short-lived and setup-only;
it can live in the keystore under a dedicated "setup" slot (encrypted at
rest like every other key, never used to sign anything real); or it can be
regenerated on each boot until setup completes, in which case the operator
re-verifies the new fingerprint. Neither is settled.

**Also settled from the spec's architecture (no open question):** the spec
puts the setup page in `ws-web`, and ws-web path-proxies `/api/v1/*` to
ws-api over the internal network, with **ws-api publishing no ports to the
LAN** — its only front door is ws-web. So the setup surface is a single
published port (ws-web's), and the setup mutation travels ws-web → ws-api
internally. That preserves the spec's "one TLS listener, no CORS" property
and means the setup window is one port rather than two.

### D20. Repos take a generic executor, so a command can span one transaction

Mutating repo methods accept sqlx's generic executor (`impl PgExecutor` /
`&mut PgConnection`), so the same method works against a pool or inside a
transaction. This is sqlx's own idiom and matches the house code, which
already reaches for `&mut *tx` versus `&pool` at different call sites.

**Why not the alternatives:**

- *Repos taking `&mut Transaction` only* — explicit, and the compiler would
  enforce that a mutation cannot escape a transaction. But it breaks Plan
  1's existing repo signatures (which the worker also uses) and forces reads
  inside a transaction to take the transaction handle too.
- *A separate write-model layer with pool-based repos* — the repos could
  not be used inside a transaction, so a command that must **read then
  write** consistently could not be. That is not hypothetical here: issuing
  against a *revisioned* profile (D5) needs exactly that, and a
  certificate issued against a profile revision that changed mid-flight
  would violate D5's guarantee.

**Consequence:** Plan 1's repo signatures widen but do not break.

### D21. Profile revisions are append-only rows, not a counter on a mutable row

An append-only `profile_revisions` table: each edit **inserts a new row**
(profile_id, revision number, the full constraint set, created_at, actor).
The `profiles` row is the identity (name, tenant, current revision
pointer). A certificate records the profile *and* the revision it was issued
under, and that revision's constraint set is always retrievable.

**Why not the alternatives:**

- *A `revision` integer bumped in place* — the old revision's content is
  gone. A certificate says "revision 3" and nobody can show what revision 3
  actually allowed.
- *A hybrid (mutable row + audit-log details)* — reconstructs the old
  constraint set from a free-form jsonb blob in the audit log, which is
  exactly the kind of "parse the audit trail to find out what was
  permitted" work that should not be necessary.

**Why append-only for a CA specifically:** a CA's value proposition is being
able to *prove what it did and why*. A profile revision IS the policy
record — the thing a certificate was checked against. The auditor's question
is "what did the policy allow when this cert was issued?", and the answer
must be a lookup, not an inference from a counter and a jsonb blob.

**Cost, and it is bounded:** an edit is an insert, and the table grows.
But profiles are edited rarely — not per issuance. The per-issuance
artifact is the certificate itself, which is stored in full.

**The race this creates, and the answer:** with revisions append-only, a
concurrent issuance and a concurrent profile edit must not interleave
badly. Two candidate mechanisms:

- *`SELECT ... FOR SHARE` on the current revision row* during issuance
  (a shared lock allows concurrent issuances but blocks an edit's
  exclusive lock), so an edit waits for in-flight issuances and an issuance
  waits for an in-flight edit. Serializes correctly, costs a row lock on
  the hot path.
- *Optimistic concurrency* — the issuance reads the revision number, and
  the insert carries the revision it validated against; a constraint or a
  conditional UPDATE detects the mismatch and the issuance is retried
  against the new revision. No lock on the hot path, but a retry loop.

The second is usually better for a hot path, and it is *strictly correct*
rather than merely serialized: the certificate records the revision it was
actually validated against, whatever happened concurrently.

### D22. A profile's SAN constraint is ONE pattern list, with syntax-distinguished entries

A profile holds a single editable list of patterns. The pattern's *syntax*
distinguishes the two SAN types that matter for a server certificate:

- a pattern containing `/` or `:` is an **IP or CIDR** pattern
- otherwise it is a **DNS name** pattern

So one list holds `*.example.com`, `example.com`, `10.0.0.0/8` — which is
what D4's "the user adds a name or a subnet later" actually wants (one
editable list, not three fields with three different editors).

**Wildcards** are permitted only as explicit `*.domain` patterns; there is
no separate "wildcards allowed" switch. A wildcard is allowed iff the list
contains a `*.` pattern. This avoids a profile that says "wildcards: yes"
with no wildcard patterns (meaningless) or "wildcards: no" with `*.foo`
present (contradictory), and it matches the "empty means unrestricted for
that dimension" logic used elsewhere in the design.

**A bare `*` is permitted**, meaning "any name" — consistent with the
pattern-list model, and guarded by the permission boundary around widening
profiles (D6): an admin who types it means it, and that admin needed the
`manage_profiles` capability to get there. This is distinct from the
*bootstrap-scoped* default profile (D3), which is closed by construction.

**Rejected alternatives:** separate typed fields for DNS / wildcard-policy /
IP-allowlist (three editors where the user wants one list); a rules
language with conditions and actions (maximum expressiveness, and a project
in itself — not appropriate for a homelab tool).

### D23. Capability checks live in the handler; one `AuthActor` type resolves all three auth methods

**Capability check in the handler (house style).** A handler takes the
actor and calls something like `actor.can(Capability::Issue)`, returning 403
if not. The house pattern already puts `AuthUser` in the handler signature
and checks `auth.role.is_admin()` inside it.

*Why not a route layer:* a `route_layer` per capability would need axum
route metadata (which it has no first-class support for) or a per-route
layer (verbose). More importantly, **the check being in the handler is
auditable** — a reviewer reading `async fn issue_certificate(actor:
AuthActor, ...)` sees the capability check two lines below, rather than
having to trace the router to learn what a route requires. The weakness of
A is that a check can be forgotten; the mitigation is a convention that
every mutating handler checks first, plus a test that enumerates the
capability each route requires.

**One `AuthActor` type for all three auth methods.** The extractor
resolves a user session, a durable API token, or a one-shot token into the
same shape, carrying: `capabilities`, `actor_type`, `actor_id`,
`auth_method`, and the session identity. Consequences:

- The capability check is uniform across all three methods.
- The audit write is uniform — one code path that writes the row, so
  D11's `auth_method` column and D16's `actor_type` distinction are
  fields of the same type rather than special cases at each call site.
- The three methods differ in exactly one place: **how the actor was
  resolved**.

### D24. The profile IS the certificate's specification — not a ceiling to negotiate against

*(Owner correction, 2026-10-21.)* The profile sets the limit; it is **exact**,
not a maximum. A request does not modulate the profile's parameters. If you
want a shorter timeframe, you create a different profile.

This replaces the "profile is a ceiling, request may narrow" framing I had
been proposing. The corrected model:

> **The profile fully determines the certificate's parameters. The request
> proposes only the subject and the names.**

Concretely:

| Dimension | Profile | Request |
|---|---|---|
| Lifetime | **exact** — the cert gets precisely this | not requestable |
| Key usages | **exact** — the profile's list, no subset logic | not requestable |
| EKU | **exact** — the profile's list | not requestable |
| SAN | the profile's pattern list is the **permitted set of names** | concrete names, each of which must match a pattern |

SAN is necessarily a permitted-set rather than an exact value: a pattern
(`*.example.com`) is not a name, so the request must supply concrete names
that the profile's patterns admit. Every such name must match; omission
(proposing no names) is a different artifact, not a subset.

**Why this is a better model than "may narrow":** it removes the subset
machinery entirely from the profile validator. There is no "is this
requested usage in the profile's list" check to get subtly wrong — the
profile's values are simply what the certificate gets. It also makes the
profile the complete, auditable statement of what a certificate may be,
which is what D21's append-only revisions exist to preserve.

**Note for the implementer:** the exact-EKU rule removes the "EKU-less is
more permissive than serverAuth" trap by construction — a profile that
names EKUs always produces them. And the exact key-usage rule means a
profile is written for a key type: an ECDSA server profile carries
`digitalSignature` only, while an RSA one carries
`digitalSignature` + `keyEncipherment`. Two profiles, not one profile with
a runtime subset rule.

### D25. A profile pins the leaf key algorithm, and the default profile uses RSA-2048

Under D24's exact model, a profile that pins key usages but not the key
algorithm can be incoherent — `keyEncipherment` is meaningless for an
Ed25519 key. So the profile pins the leaf key algorithm as well, and the
CSR's key must match.

**The default profile's key type is RSA-2048.** Two independent reasons:

- **Interop:** certbot's default key type is RSA 2048, and HAProxy and
  other common clients follow suit. A default profile pinning anything else
  would reject the majority of real clients out of the box.
- **Browser support:** WebCrypto does not implement Ed25519, so a
  browser-based CSR generator could not produce one. An Ed25519 default
  would make the manual-issuance flow impossible from the web UI the
  project is building.

*Note on the tension:* the CA's own default key type is Ed25519 (spec
line 102), and the accepted CSR key set is "ECDSA P-256/P-384, Ed25519, RSA
2048+" (spec line 89). The *leaf* default differing from the *CA* default is
intentional and should be documented, so an operator does not read it as an
inconsistency.

**This is a default, not a constraint on the system** — an operator who
wants Ed25519 or P-256 leaves creates profiles with those key types. The
built-in set of default profiles is meant to be easy and simple, and
improvable for production use.

**Consequence:** a profile is a complete certificate specification, and
two profiles differing only in key type are genuinely different artifacts
with different key usages.

### D26. Profile validation errors: specific for authorized issuers, generic for everyone else

A request that violates its profile is rejected. The *detail* of the error
depends on who is asking:

- **An actor with the `issue` capability** gets the specific reason — which
  constraint failed ("name `foo.other.com` is not permitted by this
  profile", "the CSR's key is Ed25519 but this profile requires RSA-2048").
  This is the admin who needs to understand why their request failed.
- **Everyone else** gets a generic "not permitted by policy" — they learn
  nothing about the profile's contents.

**The capability check happens first**, so the split is by authorization, not
by a separate code path per error type.

**The specific error names which constraint failed and never dumps the
permitted set.** This matters because a caller with `issue` but a
*narrower* profile could otherwise use error text to enumerate what a
*different* profile permits. So: "the name is not permitted" is fine;
"the permitted names are example.com, *.example.com, 10.0.0.0/8" is not.

## Scope (settled)

**Plan 2 is trust-boundary-first: the API, auth, and certificate profiles.
The web UI is deferred to a later plan.**

The argument: Plan 1 shipped a lot of security-relevant surface that nothing
exercises, and the API is where "who may issue a certificate" gets decided —
so designing it before the UI avoids designing it twice. The alternative
(bootstrap + UI first) was considered and set aside.

*Reinforced by D15/D16:* with three auth methods including durable API tokens
for scripting, **the API alone can serve a scripted home lab** — a home
labber can use Wardstone with no UI at all. That makes a UI-free Plan 2
genuinely useful rather than merely foundational, which was the weak point
in the argument before the auth decisions landed.

Also folded into Plan 2 regardless of scope:

- `page_size` is unbounded (`u32`) in the ws-core paging helpers — a DoS
  vector the moment an endpoint exposes it.
- `cas.parent_id` tenant consistency is unenforced — the same family of
  constraint as migration 006.

## Settled decisions

### D1. Profiles are constraints, not templates

A profile defines what a certificate **may** contain: allowed DNS patterns,
wildcard policy, IP allowlist, EKU set, key usages, lifetime cap. The API
validates the request against the profile, and the profile cannot be exceeded.

*Reasoning (owner):* favors the security side — policy is enforced by the
database rather than by admin discretion.

### D2. Homelab ease path = built-in default profiles

Ship profiles for the common certificate types so a beginner never has to
author one.

### D3. The default profile is bootstrap-scoped

The bootstrap collects the user's domain(s); the default profile allows
exactly those names (plus subdomains, per the wildcard policy) and the
admin's IPs/CIDRs. Consistent with the spec's existing "closed but guided"
ACME CIDR policy — the same shape of decision.

*Cost:* one extra bootstrap field. Certificates for names outside the scope
need a profile edit or a new profile.

### D4. Profiles must be editable and extensible after bootstrap

*Requirement (owner):* users run complex topologies — Kubernetes service
names, split-horizon DNS, new subnets, new software — and must be able to
add names, subnets, and IPs later without friction.

### D5. Profile edits are revisioned, not silently mutable

A profile edit increments a revision and is audit-logged. An issued
certificate records which profile **revision** it was issued under.

This is what lets D3's "closed by construction" coexist with D4's
flexibility: the guarantee holds at *issue* time, which is the moment it
matters. Without it, a profile's meaning is unknowable a year later — you
would be looking at a policy that changed and a certificate that predates
the change, with no way to tell whether it was valid.

### D6. RBAC has three roles

Full admin (all system config), a certificate-issuer level, and a
compliance-auditor level. The two certificate permissions are separate
capabilities: `issue` and `manage_profiles` — creating or editing the
policy that governs issuance is a different act from issuing against one.

### D7. Capability-bundle model

Roles are named bundles of capabilities; every endpoint checks a
**capability**, not a role.

The house pattern (`pm-auth/src/rbac.rs`) is a flat enum with `is_admin()`
and `can_write()`. Wardstone's certificate permissions are finer than
write/read, so the shape is extended: role → capability set, and adding a
role or a capability later touches one table rather than every check in the
codebase.

Provisional capability set:

| Role | Capabilities |
|---|---|
| `admin` | issue, manage_profiles, manage_cas, manage_users, read_audit, manage_system |
| `profile_mgr` | issue, manage_profiles, read_audit |
| `issuer` | issue, read_audit |
| `viewer` (auditor) | read_audit |

### D8. The API never touches private key material

A hard architectural boundary. Issuance is CSR-based — the private key never
leaves the client, which Plan 1's `sign_leaf_with` already enforces. No
endpoint accepts or returns a decrypted private key, **for any role
including admin**. A viewer/auditor therefore never sees key material, and
there is no key-export endpoint to gate.

### D9. The audit trail is the API's write-side contract

Every mutating API operation writes exactly one audit entry **in the same
transaction** as the mutation. If the mutation commits, the entry exists; if
the entry fails, the mutation rolls back. That is what makes the trail
evidence rather than a log.

*Consequence (real Plan 2 work):* the API needs transaction-per-operation
discipline. Plan 1's repos each run their own statement/transaction.

### D10. The audit log records writes, not reads

Reads are not logged. The trail stays a record of change, not a surveillance
record of normal operation. No sensitive-read exception is needed, because
the API never serves key material (D8).

### D11. Auth method is a first-class column on `audit_log`

The `details` jsonb was rejected for this. The house auth (`pm-auth`) tracks
`mfa_enabled` per user but does **not** record how a given session
authenticated, so this is new work. It also implies the audit row needs the
session identity, not just the user id.

### D12. Two issuance paths, split by capability

| Capability | Who | Key path |
|---|---|---|
| `issue` | issuer, profile_mgr, admin | Sign a CSR the **client** generated. The private key never exists on the server. |
| `generate_leaf_key` | **admin only** | The server generates a key, signs with it, and returns the key in the response. **Never stored.** |

The split is meaningful rather than cosmetic: the non-admin `issue` path is
one where the server *provably* cannot leak a key, because it never had one.

### D13. Server-generated leaf keys are never persisted

For a leaf certificate the CA never needs the leaf's private key — the CA's
own key signs the cert, and the leaf's key is only needed by whoever uses
the certificate. So a server-generated leaf key is generated, used to sign,
and returned. **The server never writes it anywhere.** There is no key store
to protect, no copy to leak, no re-export path, and nothing to misconfigure
later.

"Handed out once and only once" therefore stops being a server-enforced
rule and becomes a structural fact: there is no second copy because there is
no first copy. If the admin loses it, they re-issue — the same contract as a
lost API token.

### D14. "Never logged" has three concrete obligations

Not intentions — requirements for the plan:

1. The API's request/response logging must **redact** the key-bearing
   field. No access log line may contain key material.
2. Audit `details` carries ids and labels only (the schema already says
   "never key material"). The delivery gets its own action
   (`key_generated`) that records *that* a key was delivered, never the key.
3. Serialization or transport failure must not echo the body into an error
   message, and the response must not be cached.

### D15. Three authentication methods, kept deliberately separate

| Method | Who | Shape |
|---|---|---|
| **User session** | humans (browser UI, API by hand) | JWT + refresh tokens, argon2, TOTP MFA, OIDC SSO, lockout — the house pattern |
| **One-shot token** | the step-ca-style pull flow | single-use, expiring, no refresh, no identity, no session |
| **Durable API token** | scripts and automation | long-lived bearer credential, stored hashed, revocable, scoped |

The one-shot flow is **not** a user session — a machine presents a bearer
token once to get one artifact. It must not be bolted onto the session
system.

The durable API token exists because **scripting is a large potential need
for home labbers** (deployment scripts, Terraform, Ansible, HAProxy
automation). A one-shot token does not serve recurring machine use.

*Note:* the house stack has no API-token pattern to copy — only
`refresh_tokens` (LPM `migrations/001_initial_schema.sql:129`). Wardstone
defines this one fresh, so its shape is a design decision, not a port.

### D16. API tokens are first-class service identities, not user credentials

An API token is its own actor with its own capabilities, its own name and
description ("terraform-deployer", "ansible-runner"), and its own row in the
audit trail — **not** a credential hanging off a person.

This mirrors the ACME actor model the spec already commits to: *"ACME
accounts are first-class service identities owned by a tenant — not UI
users. An account is registered (key ID + JWK), and all orders and
authorizations are attributed to it."* A durable API token is exactly that
shape, and composing with the spec's model is better than duplicating it.

**Why (the reason that decided it):** audit fidelity. An auditor asking
"was this human-driven or automated?" needs the answer *in the row*, not
inferred from who owns the credential. A token tied to a user would write
`actor_type='user', actor_id='alice'` for both a click and a script, which
muddles "who is responsible" with "what credential acted."

**Consequences:**

- `actor_type` gains a value. It is currently `user | acme_account |
  system`; it becomes `user | api_token | acme_account | system`. The column
  is text, so this is a new migration, not a type change.
- A token has its own capability set, independent of any user's. The safe
  default is that a token's capabilities are **explicitly chosen at creation**
  and can only be a subset of what the creating identity may delegate —
  never more.
- Someone must be able to create and revoke service identities, which is
  its own capability (`manage_api_tokens`).

**Open sub-question:** a service identity can be tied to a user as its
*creator/owner* for accountability, while still being its own actor in the
audit trail — or it can exist with no human owner at all. The former gives
"who created this script identity"; the latter is the purer service-identity
model. **Settled: tied to a creator.** One nullable FK; it answers "who
made this script identity" without changing what the identity *is* in the
audit trail.

### D17. CA keys: model 2 — exportable, server keeps its copy

The CA's own key is required for the CA to sign anything, so destroying the
server's copy (the "offline root" model) renders the server dysfunctional.
The general rule is therefore:

- CA private keys are **exportable** — for backup, and for moving an
  offline-eligible root to offline media.
- The server **retains** its copy. Export is not a move.

*Exception the owner named:* a root that only issues certificates to sub-CAs
can be genuinely taken offline, because the root CA server itself then has
nothing left to sign. In that specific case, making the whole CA offline is
safer than merely exporting its private key. The trade-off is that such a
root cannot then be revoked by the system that holds it — the revocation
story for an offline root is the trust-anchor removal path, which the spec
already covers with the root-trust page.

## Builder check — findings that CORRECT the record above

A fresh builder read this record plus the spec, Plan 1's plan, and the Plan 1
code, and reported where it would have to guess. Four of its findings
correct something this record got wrong or left contradictory. Those
corrections are listed first; the rest are answered below or are plan-level
work.

### C1. D8 and D12/D13/D17 contradict each other — resolved

D8 said "the API never touches private key material… no key-export
endpoint to gate," for any role including admin. D12 then defined an
admin-only `generate_leaf_key` that *returns* the key, and D17 requires CA
private keys to be exportable. D8 was written before D12 and was never
revisited.

**Resolution:** D8 holds for **leaf** keys on the normal path, and is
**superseded** by D12/D13 for the admin-only generation path, and by D17 for
CA-key export. The accurate statement is:

> The API never *stores* leaf private key material. The normal issuance
> path never *has* it. An admin-only endpoint may *generate* a leaf key,
> use it to sign, and return it once — never persisted (D13). CA private
> keys are exportable for backup while the server retains its copy (D17).

### C2. The house `refresh_tokens` precedent is SHA-256, not Argon2id

This record's grounded note claimed the house stores "an Argon2id hash" of
the refresh token. **Verified false**: `pm-auth/src/refresh.rs:11,46,100,153`
uses `sha2::Sha256` throughout, despite the migration's comment claiming
Argon2id. So the precedent for hashing a *bearer* credential in this
house is SHA-256, not a password KDF.

**Consequence:** the "what KDF do we hash API tokens with" question is now
open and needs a deliberate answer rather than a port. (Argon2id is
deliberately slow and is for *passwords* — a high-entropy random token
needs no KDF slowdown, and SHA-256 of a 256-bit random token is the
standard practice. But it should be a decision, not an accident.)

### C3. `ws-ca` has NO EKU support at all — the profile model's EKU dimension needs engine work

Verified: `LeafSpec` has no EKU field, and `sign_leaf_with` never sets
`params.extended_key_usages`. rcgen 0.14.10 supports it
(`CertificateParams::extended_key_usages`), so the change is small — but it
is a change to **Plan 1's CA engine**, not a Plan 2 addition.

Related and sharper: **an empty EKU list is MORE permissive than
`serverAuth`**, and the same holds for an empty key-usage list (RFC 5280
§4.2.1.3: an absent extension means unrestricted). Plan 1 sets
`params.key_usages = spec.key_usages.clone()` unconditionally, so an empty
list currently yields a certificate with **no KeyUsage extension** —
unrestricted. That is the same reading Plan 1's own `ensure_issuer_is_ca`
already applies (ca.rs:234). So D24's claim that the exact-model "removes
the trap by construction" is **only true if empty lists are illegal**. The
profile validator must therefore forbid empty EKU and empty key-usage
lists, and `sign_leaf_with` should refuse them too.

### C4. D22's pattern-syntax rule misclassifies bare IPv4

D22 says "a pattern containing `/` or `:` is an IP or CIDR pattern;
otherwise a DNS name." But `10.0.0.5` contains neither, so it takes the
DNS branch and can never match an IP SAN — while D3 says the default
profile covers "the admin's **IPs**/CIDRs." (A bare IPv6 `fe80::1` does
contain `:` and is fine.)

**Resolution:** the rule needs a third branch — **try to parse the pattern
as an IP literal first**; if it parses, it is an IP pattern; else if it
contains `/`, it is a CIDR; else it is a DNS name.

### C5. D1's and D3's "ceiling" vocabulary is stale

D1 and D3 speak of a "lifetime cap," an "IP allowlist," and a "wildcard
policy" as separate fields. D22 and D24 superseded all three (one pattern
list; exact values, not ceilings). D3's cross-reference to "per the wildcard
policy" dangles, because D22 deleted the wildcard-policy field. The
profile model is D22 + D24; the older wording should be read as historical.

**Decisions still needed from the owner (Tier 1):**

1. **Plan 2's deliverable boundary** — the Scope section says "API, auth,
   profiles, web UI deferred," but D18/D19 put a setup *page* in `ws-web`
   behind a TLS listener, and Plan 1's own preview promised Plan 2 =
   "Bootstrap, profiles, auth, API, UI… frontend scaffold + auth pages,
   Root Trust page, compose bundle." Three different scopes. Also open:
   are user-management, CA-management, and tenant-creation endpoints in
   Plan 2? And is the full house auth surface in scope (JWT + refresh +
   argon2 + TOTP + OIDC SSO + lockout), or a scoped subset with TOTP/OIDC
   deferred?
2. **The final capability set** — D7's table is explicitly labelled
   "provisional" and is missing `generate_leaf_key` (D12),
   `manage_api_tokens` (D16), and **any read capability** (a viewer must
   read certificates, so a read capability is implied but unnamed). Also:
   is the role→capability mapping a table or an enum column, and may a
   user's capabilities exceed their role's bundle?
3. **The profile's relationship to the CSR and the subject** — Plan 1 takes
   SANs from `LeafSpec` (not the CSR) and the CN from the CSR. If the
   request body carries the names, must they equal the CSR's SANs or is the
   CSR's SAN extension ignored? And is the subject CN itself a permitted
   name under the profile, or exempt? (A subject carrying a name the
   profile does not permit is a real policy hole.)
4. **Which key algorithms a profile may pin, and how a CSR's key is
   compared** — a new leaf-key enum, or an extension of the CA `KeyType`
   enum? Does a profile pin "RSA" (any size ≥2048) or a specific size?
   (Today `CsrInfo` cannot distinguish RSA-2048 from RSA-3072.) And must
   the admin-only generation path be able to generate P-256?
5. **The SAN pattern matching semantics** — does `*.example.com` match
   `example.com` itself, and how many labels deep (`a.b.example.com`)?
   Is matching case-insensitive? Does the bare `*` admit IP SANs as well
   as DNS names?
6. **The built-in default profiles' content, and how they get seeded** —
   built-ins cannot be seeded by a migration (the default tenant is
   created by setup, and Plan 1's `connect` depends on `tenants` being
   empty on a fresh DB), so they are created by bootstrap code — which then
   needs a per-tenant seeding path for the second tenant the spec allows.
7. **A one-shot token's identity and authoriser** — D15 says "no
   identity," yet something must authorise the CSR submission. What is the
   `actor_type` for a one-shot-issued certificate, and does the audit row
   record the human who minted the token?

**Answered by ruling (no owner input needed):**

- *`auth_method` column values and nullability* — follow `actor_type`'s
  shape: one value per auth method (`session`, `api_token`, `one_shot`),
  NOT NULL, since every audit row has an actor. Session identity is a
  first-class column (D11) — the house has no `sessions` table, so the
  session id is the refresh token's id.
- *`certificates.profile_name`* — replaced by a FK to the immutable
  revision row (`profile_revision_id uuid`), because D21's "the revision IS
  the policy record" argument supports pointing at the revision itself.
  The name survives only as a denormalised label on the revision row.
  The revision's constraint set is stored as **typed columns**, not a jsonb
  blob — the same reasoning D21 applied to the audit log.
- *The profile↔actor binding* — **not a feature in v1.** The capability
  set is the only scoping mechanism, so every `issue` holder can use every
  profile. D26's specific-vs-generic error split is therefore a UX choice
  for all issuers, and its "narrower profile" paragraph is superseded.
- *Exact lifetime vs the issuer clamp* — the API **pre-checks and refuses**
  ("this profile's lifetime exceeds the issuing CA's remaining life") rather
  than silently issuing a shortened cert, because a cert that does not
  match its profile violates D24. The API reads the CA's `not_after` to
  make that check.
- *The D21 race mechanism* — **optimistic concurrency**, confirmed. The
  issuance reads the revision it validated against and the write carries
  it; a mismatch is detected and the issuance retried against the new
  revision. (The "conditional UPDATE" does take a row lock, so "no lock on
  the hot path" is only partly true — the correctness argument, not the
  lock-freedom, is the reason to prefer it.)
- *`allocate_serial` and the transaction* — it **joins the issuance
  transaction**; a rolled-back issuance burns a serial, which is
  acceptable and is the conservative choice (serials are never reused).
  Its signature changes to take the executor.
- *Repo executor shape* — **executor as a parameter** on every method
  (not a repo-over-executor), because the house pattern constructs repos
  over a pool and this preserves that. It is a signature change across
  Plan 1's five repos and `ws-ca`, not a pure widening — D20's wording
  was too optimistic.
- *The setup cert's key* — a **dedicated keystore slot**, not per-boot
  regeneration: per-boot regeneration means the operator re-verifies a new
  fingerprint on every restart, which defeats the fingerprint-verification
  UX D19 proposes. This extends `KeyStore` with a setup-key slot.

**Plan-level work (not questions):** the `cas.parent_id` tenant-consistency
FK (migration 006 already provides `cas (id, tenant_id)` unique, so the
composite FK closes it in the same idiom); a shared `paging()` helper with
a maximum (Plan 2 adds three more repos); the audit action vocabulary and
the `details` jsonb shape.

**Note from the check:** the workspace has no `axum`, `tower`, or
`jsonwebtoken` dependency yet and `ws-auth`/`ws-api`/`ws-web` are empty
stubs — so Plan 2 introduces the HTTP and JWT stack from scratch, while
the auth *schema* is a genuine port of `pm-auth` (`users`, `user_groups`,
`refresh_tokens`, `oidc_config`, plus `012_account_lockout.sql`'s
`failed_login_attempts`/`locked_until`).

## Grounded notes (verified in the tree)

- The **only** production audit write in the entire codebase today is the
  worker's `crl_built` entry (`ws-worker/src/jobs.rs:139,169`).
  `ca_created`, `cert_issued`, `cert_revoked`, and `key_generated` exist
  only in **test fixtures** — the smoke test asserts them because the test
  writes them. The API is where the real writers land.
- `certificates.profile_name` is currently free-form text
  (`migrations/002_certificates_and_revocation.sql:21` — "free-form label in
  v1; profiles table is Plan 2"). Under D1 this becomes a real reference, and
  the profile's own constraints need a table.
- The house auth crates: `pm-auth` is the fuller one (jwt, mfa_totp,
  mfa_webauthn, password, rbac, refresh, session); `fw-auth` is the smaller
  one (jwt, password, rbac, session).
- **The house user schema** (`linux-patch-manager/migrations/001_initial_schema.sql:85`)
  is directly reusable: `users` with `role`, `auth_provider`
  (local/azure), `password_hash`, `totp_secret`, `webauthn_credential`,
  `mfa_enabled`, `azure_oid`, `is_active`, `force_password_reset`,
  `last_login_at`; plus `user_groups` for group membership, `refresh_tokens`
  (Argon2id-hashed opaque token bytes, sliding expiry, revocation), and
  `oidc_config` (migration 014). Wardstone needs the same shape with a
  tenant column and the capability-bundle role from D7.
- The house `refresh_tokens` pattern is the direct precedent for the
  one-shot key delivery in D13/D14: **the token bytes are never stored —
  only an Argon2id hash**, so a stolen database row cannot be replayed. The
  same reasoning applies to a one-shot delivery token.
- The house auth's `mfa_enabled` is a per-user boolean and does not record
  how a given session authenticated — confirming D11 is new work rather
  than a port of an existing column.
