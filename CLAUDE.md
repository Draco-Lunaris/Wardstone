## Build, Lint, and Test

- Lint: `cargo fmt --all -- --check` and `cargo clippy --workspace --all-targets -- -D warnings` — both must be clean for every commit.
- Fast tests (no database): `cargo test --workspace`.
- DB-gated tests: `DATABASE_URL=postgres://wardstone:wardstone@localhost:5432/wardstone_test cargo test --workspace -- --include-ignored` against a live Postgres with that database.
- One suite: `cargo test -p <crate> --test <suite_name> -- --include-ignored`.
- House style: no `unwrap()`/`expect()` outside `#[cfg(test)]` modules (typed error enums); short conventional-commit subjects; **no AI co-author attribution** in commits.

## DB-Gated Test Conventions (binding)

- Test DB: `postgres://wardstone:wardstone@localhost:5432/wardstone_test`.
- Every DB-gated suite takes a unique advisory-lock key from the `0x0057_4144_5354_00xx` family — **0003 through 0020 are taken** (`0018` = `ws-core rotation_test`, `0019` = `wardstone disk_scan_test`, `0020` = `wardstone log_sentinel_test`; the earlier assignments follow their `ADVISORY_KEY` comment); the next free key is `0021`. Never reuse a key.
- Every suite sweeps its own rows (FK order) BEFORE each test and **DELETEs the rows it created at the END of each test** — `crates/ws-core/tests/db_test.rs` snapshots the tenant-name set before/after and proves `connect()` itself never seeds a tenant.
- **Suites that rotate the shared `wardstone` role's password** (setup POSTs run the at-creation rotation that seals the fresh credential into `db-credential.envelope`, and the recovery arm re-seals the same way; the api unlock builder rotates per unlock) MUST: take the process-local tokio-mutex fence BEFORE the fixture connect (the advisory lock cannot order the pre-lock connect); restore the role over the fixture's DEDICATED pre-rotation connection — never the pool, which may open a fresh connection exactly when the password is rotated — BEFORE any post-rotation DB read; and (the reference implementation: `ws-web tests/setup_test.rs`'s `RestoreNet` + `a_fixture_dropped_mid_rotation_restores_the_shared_role`) carry a panic-safe Drop net so a test unwinding mid-window cannot poison every later suite with misleading `28P01`s. A poisoned role resets with `sudo -n -u postgres psql -c "ALTER USER wardstone PASSWORD 'wardstone';"`.
- Migration files in `crates/ws-core/migrations/` are edited in place while the project is pre-release (every deployed database is a disposable dev install); from the FIRST RELEASE they are ADD-ONLY — sqlx checksums them (SHA-384 over raw bytes), so editing an applied migration breaks every deployed database. Bump `REQUIRED_MIGRATION_COUNT` in `crates/ws-core/src/db.rs` when adding one; `connect()` runs migrations before the count check.
- The ws-secmem arena suites need the test host's memlock rlimit at/above the 512 MiB budget (536870912 bytes — the production pool's ceiling; the boot names the exact setting in its refusal). echo-dev runs as an unprivileged LXC, so the hypervisor host grants it via `lxc.prlimit.memlock: 536870912`.
- The socket-form battery needs echo-dev's PostgreSQL HBA line `local wardstone_test wardstone scram-sha-256`, sitting above the default peer line in `/etc/postgresql/16/main/pg_hba.conf` (backup: `pg_hba.conf.pre-task10`; whether it stays past this plan is decided at plan end, not per-task).

## Architecture

Crate graph (acyclic): `ws-core` (SQLx Postgres persistence: models, tenant-scoped tables, executor-agnostic stateless repos taking `&mut PgConnection`/executors — see `user_repo.rs` for the house idiom) ← `ws-ca` (engine: CSR validation, issuance/revocation, EKU, key-usage, pinned leaf keys with EXACT-size refusal, the `KeyStore` holding every CA key as a master-key envelope — per-use unwraps through `with_ca_key`, the serving-key-holder and batch-signer allowances through `unwrap_ca_key`, and no plaintext key slot at all — advisory-lock serial allocation) and `ws-auth` (argon2id, Ed25519 JWT with the `jwt-keys.envelope` pair — the signing key is arena-held DER, sealed since setup — TOTP, generic OIDC SSO, service identities/API tokens/refresh tokens, lookup-only one-shot tokens) ← `ws-api` (axum REST `/api/v1/`: per-route capability checks, the CoreError→ApiError mapping table, transactional audit — a mutation and its audit row commit on the same transaction — GCRA rate limiting on auth routes; the sealed shell answers `503 sealed` until the unlock relay lands over its `SO_PEERCRED`-gated Unix socket) and `ws-web` (TLS front door via `axum-server`/ring, `/api/v1` path proxy with bounded timeouts, first-run setup page conditionally mounted only while the default tenant is absent; setup mints tenant/root CA/admin/two profiles/CA-issued leaf key-before-row, writes every key's FIRST copy as its passphrase-sealed envelope — `master.envelope` last, the sealed marker — and swaps the serving leaf in place through the resolver: the swap IS the reload, no process exit) ← `wardstone` (single binary, `ui`/`api`/`db-verifier` modes; the boot dispatches on `master.envelope` alone — absent → the first-run setup page over a RAM-only certificate with NO database connection, present → the locked page, the unlock is the only door; the api's unlock is `load_sealed`-only: a missing `jwt-keys.envelope` is the typed `jwt_envelope_missing` refusal BEFORE any secret unwrap or DB touch, never a mint; a sealed volume whose database holds no tenant is the fatal interrupted-setup refusal; unlocked boot TLS resolves the newest `status=active AND profile_name="web-server"` certificate row + `keystore.unwrap_ca_key(cert.id)` — no servable active leaf keeps the sealed boot certificate serving with a WARN, a corrupt envelope is a hard boot failure). Underneath both modes `ws-secmem` is the locked-memory arena (`memfd_secret(2)` pages — never swapped, never core-dumped, invisible to ptrace/`/proc/<pid>/mem`; a 512 MiB memlock budget) holding every unlocked key, token, and session at rest-in-RAM — seal-at-creation: no plaintext key file ever exists on disk. `ws-worker` runs post-issuance jobs (CRL/OCSP regeneration) against ws-ca — one arena unwrap per CA per batch tick. **Plan 4 delivered ACME**: the `ws-acme` crate (first-party RFC 8555 — JWS verification with alg-key pinning, RFC 7638 thumbprints, the single-use nonce store; challenge arithmetic) served through `ws-api`'s `/acme/{tenant}/…` machine surface (JWS + `problem+json`; Replay-Nonce on every response) and visible via `/api/v1/acme` REST (`read_acme`/`manage_acme_accounts`); `/acme/*` and `/api/v1/*` both path-proxy through ws-web; per-IP enrollment GCRA at the ws-web edge, per-account limiter with `WARDSTONE_ACME_ACCOUNT_LIMIT_DISABLED`; `WARDSTONE_PUBLIC_URL` is the absolute-URL base (Host never trusted).

- Token families by prefix: `ws_rt_` refresh, `ws_at_` API/service-identity tokens (`ws-at_`-shaped lookups are hash-only), `ws_ot_` one-shot (redeem ONLY at `POST /api/v1/certificates/pull`, which claims it inside the issuance transaction; any other route 401s a `ws_ot_` bearer without burning it).
- Deploy: `docker/compose.yml` (one image, `wardstone ui` + `wardstone api` + `db` Postgres; **only ws-web publishes 8443** — ws-api binds TCP 8080 on the internal compose network plus its `SO_PEERCRED` relay socket, nothing published; the bundled db binds no TCP at all, its traffic rides the shared unix socket, and both socket directories are host bind mounts with a documented once-per-boot pre-step; required envs fail loudly) and `docker/README.md` (JWT envelope recovery: none in-product — a missing or corrupt `jwt-keys.envelope` fails the api unlock loudly before any DB touch; restore the volume from backup or wipe both volumes). The image contract is no ENTRYPOINT with the `wardstone` binary on PATH.

## Conventions That Differ From Tool Defaults

- Where an enum is stored in a TEXT column, `as_str()` must equal its serde name, and serialized DTOs use `#[serde(rename_all = "snake_case")]`.
- Workspace dependency pins live in the root `Cargo.toml` with an inline rationale comment at the pin site (each consuming task added only the pins it uses).
- `ws-web` selects the rustls `ring` provider explicitly — `aws-lc-rs` must never enter the graph (its build needs an absent C toolchain); verified via `cargo tree -e features -p ws-web`.

## Project Intent

From `README.md`: Wardstone is a self-hosted certificate authority with a web UI — simple enough for a homelab and hardened enough for production.

The "hardened enough for production" clause is a design constraint, not marketing copy: CA key handling, issuance/revoke flows, and the web UI's attack surface are security-sensitive, and choices in this space should be treated accordingly even in early scaffolding.
